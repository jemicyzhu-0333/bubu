# Theme state ledger v1: executable boundary

Pure CPU state module, no production adapter, renderer, inventory or network calls. Frozen runtime remains unchanged. User-confirmed r3 policy: routine default 600 seconds, explicit overrides 600..900; feed exactly 30; historical completion never activates; edits never extend; semantic generation (not raw occurrence) defines idempotency.

## Trusted input boundary

This module accepts events only from a future authenticated, postcommit adapter. `postCommit: true` is a schema assertion, not authentication or proof of durable commit. Production wiring is deliberately absent. Namespace configuration must identify a stable account/business producer, never a connection epoch. All identifiers are bounded nonempty strings of at most 128 UTF-16 code units; all times and counters safe integer milliseconds/counters.

A semantic completion is identified by `(namespace, sourceKind, entityId, completionGeneration)`. `entityId` may be the reusable occurrence slot; upstream must issue a genuinely new completionGeneration only for genuinely new completion. Recompletion after undo of the same semantic completion retains generation. Feed uses stable transaction/command identity as entityId. No renderer inference is permitted.

Each semantic completion additionally has a namespace-unique, monotonically allocated `completionOrdinal`, reserved durably by the business adapter. This is immutable across revisions, mapping changes, reconnect and retries. Revision is a positive source-local ordering number. Gaps are allowed only because every event is a complete current-state snapshot of that semantic completion, including original completion identity/time/mapping/origin and a monotonically nonincreasing `deadlineOccurredAt` watermark. This watermark is the earliest completion time ever applied to the instance; it prevents reorder from losing a prior shortening. Notes edits and same-generation recompletion preserve it. Corrections earlier can lower it; corrections later cannot raise it.

Event fields: schemaVersion=1, namespace, eventId (opaque bounded delivery identity), transactionId (business operation commit), sourceKind=routine|feed, entityId, completionGeneration, completionOrdinal, revision, operation=complete|correct|edit|revoke, completionState=completed|revoked (complete/revoke must match; edits carry authoritative current status), origin=live_completion|historical_backfill|history_edit|recovery_sync, postCommit=true, replayed=false, occurredAt, committedAt, receivedAt, timeDomain=trusted_utc_ms, original={occurredAt,committedAt,origin,definitionId,mappingVersion}, deadlineOccurredAt, revokeReason (nonempty for revoke, null otherwise).

`original` is immutable and refers to first successful semantic completion, including when first delivery is a revoke or edit. `occurredAt` is current effective completion time. `committedAt` is current operation commit time; `receivedAt` is diagnostics only. Original and current times cannot exceed commit, commit cannot exceed received, received cannot exceed authoritative now. deadlineOccurredAt <= original.occurredAt and current occurredAt. No epsilon, local receipt heuristics or future tolerance. Revision changes must not reduce committedAt or increase deadlineOccurredAt. A historical original can never be promoted to live. A first-seen edit/correct/recovery event is recorded but cannot create activation; first-seen revoke records a tombstone. A current complete with live origin and live original can activate only if initial admission qualified. Unknown mapping/capability outcomes are pinned for this completion forever.

Events with replayed=true are receipts, not postcommit source events; rejected without mutation. Genuine durable replay uses the original event unchanged, including replayed=false, with delivery receiving time updated. Same revision content equality excludes eventId and receivedAt; content conflict rejects the whole batch. An edit/correct full snapshot may reflect a missed intermediate revoke or same-generation recompletion, thus may change active status of an already-qualified completion. It still cannot extend the deadline or create eligibility for an initially ineligible completion. This does not license a text editor to invent a recompletion: the future adapter must copy authoritative completion state. Higher revision is a full authoritative snapshot; older revisions never overwrite or revive.

## Bounded identity and sealing

Checkpoint IDs are diagnostic authority references; only the most recent is retained per namespace, and global uniqueness/reuse is not audited. The monotonic ordinal watermark, not checkpointId uniqueness, enforces the replay barrier. After compaction, verifying that an old identity was not fraudulently assigned a fresh ordinal is necessarily an upstream invariant; the ledger cannot provide unconditional permanent dedup under a producer that violates the immutable ordinal/identity contract.

No unbounded eventId Set: bounded per-completion latest revision and canonical semantic payload replace delivery-level storage. Duplicate semantic revision with a different eventId is idempotent. EventId is diagnostic, never sufficient authority or TTL identity. Producer MUST NOT reuse an eventId for different semantic content; this module does not globally audit that external invariant. Core replay safety rests on business identities and revision.

State holds at most maxRecords total records across a fixed namespace list. v1 admission ceilings: 4096 records, 32 namespaces, 256 mappings, 256 capabilities, 64 required capability references per mapping. These are prototype resource limits, not a claim about a production retention duration. Production event rates/checkpoint cadence must be established before wiring. Unknown namespaces fail closed. At capacity, new identities reject atomically rather than evict dedup history. `seal(namespace, throughOrdinal, checkpointId, now)` is an EXPLICIT adapter checkpoint: authority guarantees every completion <= throughOrdinal is permanently closed, no unseen eligible completion or future modification in that range can arrive, and archive/business replay has durably acknowledged this boundary. It is not a wall-time TTL garbage collector. Sealing rejects if a record in that range could still be active (including revoked sources with unexpired original eligibility, since same-generation recompletion might otherwise be possible). Then records <= the watermark are removed and all later deliveries <= watermark reject as sealed history forever. A single persisted watermark per configured namespace keeps memory bounded without silently forgetting old identities. The module cannot verify the authority's seal assertion; calling it without the protocol breaks recoverability. Without upstream seal support, capacity remains a hard explicit blocker.

## Time, snapshots and recovery

Caller supplies trusted UTC now monotonically nondecreasing for every transaction/query. Within a process a clock adapter must anchor UTC to monotonic elapsed time; OS wall-clock rollback must not be passed directly. Across restart a fresh trustworthy UTC anchor no earlier than the snapshot's lastNow is required. If not available, restoration fails closed. No hidden/freeze input changes time; caller must advance actual fact time before asking eligibility.

Snapshots include exact config, pinned mappings/outcomes, all records, namespace sealing watermarks and lastNow. Snapshot import must strictly validate schema and all invariants; no reinterpretation using new registry. New config migration is out of scope. Snapshots are trusted data exported by this module, not signed authority. Storage adapter must durably atomically persist snapshot plus upstream cursor BEFORE exposing new eligibility or acknowledging delivery. This repository supplies a file-based recovery demonstration but does not certify power-loss/outbox correctness or production storage. Loss/rollback of acknowledged snapshots requires authoritative reconstruction/checkpoint, never an empty fresh ledger pretending replay safety. Recovery restores remaining eligibility only and does not emit visuals/actions.

## Mapping and capability gate

Exact `(kind, definitionId, mappingVersion)` lookup only. Each record contains themeId, recipeVersion, approved flag, presentationMode=overlay_only|overlay_and_actions, overlayPolicyId, actionPolicyId (required for actions), requiredCapabilities, assetPolicyDigest and optional routine durationSec. Capabilities explicitly list approved+runtimeReady and channel=environment.overlay|body.action|face.semantic|prop. Pure registry validation checks declaration shape, mode/resource correspondence and required policy references. It does NOT certify resource arbitration or artistic readiness. Missing/unapproved/unready mappings yield permanently ineligible ledger facts; no fallback. Production registry is empty; tests are visibly fixture-only.

Projection lists active FACT eligibility per theme and independent source deadlines. It always reports selected=false, visible=false, performing=false and never claims channel allocation. Max deadline is a union, not addition. Focus base selection, overlay leases, action arbitration, sparse scheduling, late asset release and animation ownership are intentionally not implemented here. No event can write base background, detection state, or inventory. Full r2/r3 renderer cases remain deferred; they cannot be reported as passing by testing this module.

## Recoverability resource proof

A fully populated event has 27 data nodes, a first/latest record has 55. 4096 records consume 225280 nodes; worst allowed config/seals adds fewer than 25000, below the fixed 1000000-node scanner budget. IDs are bounded to 128 code units. A conservative serialized envelope bound with all arbitrary characters JSON-escaped is below 96 MiB; the file reader limit is 128 MiB. Test capacity.test.mjs constructs every configured structural maximum with long escaped identifiers and verifies export/restore. Raising any ceiling requires updating this proof and the joint maximum test, not simply raising the scanner budget.

Package minimum is Node.js 20; this closure was actually executed on Node.js v24.19.0. The core uses node:util only to reject Proxy inputs before trap execution. A browser bundle/adapter is not provided.

## Missing initial evidence and ordering diagnostics

First-seen edit/correct/revoke with a live original returns admissionReason=needs_reconciliation and needsReconciliation=true. It is recorded, not silently dropped, and does not gain eligibility from a later same-generation complete. The explicit recovery interface is restoreLedger(authoritativePreviouslyAcceptedSnapshot, now), replacing the caller's ledger only after successful validation; the authority must have retained the original accepted evidence. It must not fabricate a snapshot from a bare edit. True historical/recovery-sync input remains nonlive_or_noncompletion, not a request to replay old history.

Ordering is not universally commutative:
- complete v1 then revoke v2: admitted then revoked; same-generation complete v3 can restore only original remaining eligibility.
- revoke v2 first then complete v1: needs reconciliation; v1 is stale and cannot revive.
- edit/correct v2 first then complete v1: needs reconciliation; v1 is stale.
- one atomic batch containing complete v1 and revoke/edit v2: both evidence items are present; sort by identity/revision, process complete evidence then newer state, emit one final projection.
- higher complete/edit/correct snapshots after known admitted success may reconcile skipped intermediate revisions only because they carry authoritative current completionState and nonincreasing deadline watermark.

These are deliberately different evidence conditions. Tests never claim all arrival permutations produce the same acceptance provenance.

The checkpoint reader pre-stats a regular file, rejects size >128 MiB before reads, reads <=64 KiB chunks with a total byte ceiling plus one sentinel byte, then rejects observed size/mtime changes. Checksums catch accidental corruption, not malicious trusted-directory modification with forged metadata and checksum. No production power-failure or durable outbox certification is implied.

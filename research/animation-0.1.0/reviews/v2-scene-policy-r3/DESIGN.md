# V2 r3：已设计预设触发的限时主题

状态：规范草案，不是实现或运行验收。r2与更早历史保持冻结。来源：用户消息Sentinel_a99016d86ab48191becd2b526218a5c9。

## 1. 已明确的产品方向

- 用户成功完成预设日常，且该预设已有我们设计的主题映射，才激活对应“xx时间”；如咖啡、健身。
- 日常来源持续10–15分钟。每个预设配置必须显式选择600..900秒，本版不暗填精确默认。
- 成功给桌宠喂食，且该食物命中已设计映射，可激活较短同类主题。用户举例30秒；本版首批建议显式feedDurationSec=30，若将来需要其他值须另外修改政策。
- 主题持续不等于动作持续循环。主题装饰保持；可兼容的短动作只在经批准的稀疏机会执行，实际频率/动作选择尚未批准。
- r2专注基础背景继续锁定；兼容环境overlay可叠加，占用身体/手/socket/脸的动作按资源仲裁。关闭活动检测不能撤销日常或喂食主题来源。

新增方案不意味着所有V1日常/食物自动获得3D主题。咖啡、健身只是主题示例；其真实资产是否完成、预设ID与食物ID映射仍须逐项核实，未完成能力门保持inactive。

## 2. 推荐的最小语义

把主题看成“一个主题ID + 多条独立有效来源”，每条来源有自己的期限；把表现配方看成从当前有效主题派生的计划。

- 同主题日常10分钟+喂食30秒同时存在：保留两条来源，主题有效至最后一条有效来源到期；短喂食不能覆盖长日常，也不把30秒加到日常后面。
- 日常撤销只撤销该条来源；若喂食仍有效，主题继续到喂食自己的期限。其他日常来源同理。
- 同一成功事件重复送达、网络重试、历史同步不创建第二条来源、不重新采样时间、不重启TTL。
- 同一个日常发生实例（occurrence）完成后撤销再完成，建议仍复用原实例键与首次成功的时间上限，不能反复点完成延长主题。真正不同的日常实例可提供独立来源，但不按事件次数累加时长。
- 主题结束时撤销该主题待执行装饰/动作资格并释放自有资源；正在执行短动作必须遵从批准的安全退场，不硬跳姿势。主题被抢占时期限仍流逝，不因屏蔽、隐藏或恢复重新计时。

以上合并、幂等和防续时为本次推荐规则，不能被误读成已经实现。

## 3. 映射与能力门禁

映射注册项必须由稳定presetId/foodId引用themeId，不能按“标题包含咖啡”模糊匹配。配置绑定版本与已批准资源/策略摘要；同一业务事件采用事务提交时确定的映射版本，后续修改映射不追溯复播历史事件。

资格链：业务成功事务 → 来源事件验证与幂等 → 已设计映射存在 → theme配方与能力就绪 → 建立限时来源 → 求兼容展示。

点击完成按钮、乐观UI、请求已发出、喂食动画开始、库存扣减失败、失败重试、取消或未确认成功，均不激活主题。喂食由既有业务事务确认成功后发出事件；主题层不自行扣库存、不把动画播完当喂食成功。完成日常也以业务已持久确认结果为准，而非界面状态。

建议把能力门拆为：
1. 概念映射已设计且批准（theme存在）。
2. overlay或动作配方存在且声明通道/兼容。
3. 实际运行资产已审核、当前能力版本支持。

只有overlay可用时是否允许overlay-only，由该映射显式批准；不得因body能力缺失自动宣称完整主题已支持。配方未设计/未批准或配置缺字段：拒绝激活并可诊断，不能回退到另一主题。资源临时加载未完成：事实有效期从成功事务起算，不从加载完成起算；加载结束时若来源已过期，释放结果，不补发一整段主题。

## 4. 来源事件、幂等与撤销

建议上游事件至少包含：eventId（投递去重）、transactionId、sourceKind（routine/feed）、sourceInstance、occurrenceId或feedTransactionId、sourceVersion、presetId或foodId、outcome、completionOrigin、committedAt、effectiveCompletedAt。

- eventId处理同一通知的重复投递；业务幂等键另用具有完成实例代际的routine completion identity或feed transaction，避免上游重发换eventId绕过去重。
- sourceVersion决定同来源修改/撤销顺序。过旧update/撤销不得清除新来源实例；撤销先到、较旧成功后到不能复活。
- 不对未来时间戳猜测或加epsilon。时间域、可信来源、上游原子提交契约不满足时拒绝/隔离，不自动激活。
- 已接受事务必须记录“已处理/无映射/不合格”等结论及版本，使后来新增映射不会把旧event重放为新主题。去重记录的持久化、恢复与有界保留必须跟业务重投窗口协调；不能仅存内存Set再重启后重播。具体保留期本版不擅定。
- 仅来源自己的匹配事件，或授权的有效性/撤销管理器可清除来源；保持原因。检测开关只清检测派生事实，不能clear-all主题。

## 5. 完成时刻、补录与修改（推荐方案，需确认）

推荐把“当下真实完成”与“历史补录/编辑旧记录”分开：

| 情况 | 推荐主题处理 |
|---|---|
| 当下成功完成，实时事件 | 起点为确认事务携带的真实完成时刻，终点=起点+该预设显式时长 |
| 传输/渲染延迟 | 只剩余有效时长，不从收到事件或加载完成时重新开始 |
| 历史补录、导入、恢复同步 | 不自动激活当前主题；不是把过去10分钟搬到现在 |
| 迟到但确属实时提交事件 | 只在原截止前有效；已到期直接记处理、不显示 |
| 修改文字/备注且发生实例及完成状态不变 | 不重启、不延长 |
| 改完成时间 | 重新校验对应业务记录；建议允许缩短或过期，不把截止延长到首次接纳截止之后；若要重新激活需显式新操作 |
| 撤销完成/撤回成功事务 | 只撤销对应来源，不清同主题其他有效来源 |
| 同一日常实例撤销后再完成 | 建议保留首次成功截止上限，不无限续时；不同真正发生实例可新建来源 |
| 未来时间/来源时间无法确认 | 不自动激活；交业务层处理 |

历史与实时必须由可靠事务语义或明确用户操作类型区分，不能仅凭“收到时间近”判断。未定义来源origin或时间校准契约时，激活门保持关闭；不自行设“5分钟内算实时”等阈值。

这里的时间是主题事实有效时间，不是face owner的可见逻辑时钟。隐藏时TTL继续；恢复时先更新期限/撤销再求展示。系统时钟更改、跨重启恢复需明确wall-to-monotonic映射与持久记录；不能通过重建owner给主题重新分配全额时长。

## 6. 装饰、稀疏动作和多主题

主题拥有environment.overlay集合；coffee可表现咖啡主题装饰、fitness可表现健身主题装饰，但美术/空间占用未批准，不预填具体物件。多个主题可同时有效；仅兼容配方叠加，不同主题不能无限堆满屏幕。容量/遮挡冲突须有批准规则，无规则则配置不可激活。

短动作是从有效主题派生的独立一次性意图，必须声明所需body mask、hand/socket、prop、contact及可选face。建议机会点只发生在批准的时刻/空闲边界，并有有限频率/每主题预算；本版不填间隔、概率或重复次数。稳定装饰不需要循环动作；主题还有效也不代表立刻补做所有错过的动作。

AI/coding/music等活动与主题事实并存。占用冲突按r2批准策略决定，主题不会因为用户正在AI协作就消失；动作被拒绝或取消也不延长主题TTL。动作完成不消费主题时长、不缩短另一来源；若要“一次主题最多喝一次”等规则，写入显式动作资格预算。

禁用检测不影响日常/喂食来源；routine/feed撤销不影响真实AI/music来源。主题/动作/道具异步计划均带sourceVersion、plan generation、focusSessionId（如依附本session）；过期或撤销后晚到结果必须释放，不attach。

## 8. 交付与验收边界

CONTRACT.json是可机读的拟议契约/约束描述，不是已接入schema；EXAMPLES.json为符号例子，不含伪批准的资产或日常精确时长；DECISION-TABLE.json为待执行真值表，不是运行测试结果。

实现前先冻结上述未定语义，再对纯事实账本/合并/来源时间与幂等写测试。之后做资源计划与renderer接入。owner08仍仅提供七槽固定单次脸的CPU/API底座；主题来源、持久幂等、overlay、真实身体道具、稀疏调度及GPU仍缺失，不因本规范存在而变成已支持。

## 9. V1现有事件适配差距（源码核查协作初核）

ff711d9的routine-logged只在transaction.committed之后发布，已有routineId/occurrenceId/status/kind/scheduled/at/dayKey/revision；但时间修正也用同一种事件，缺operation/origin，不能直接判为新完成。undo是独立routine-log-undone。

喂食companion-fed是postcommit事实，已有fedAt/revision/foodId；现fact未带commandId，持久receipt有commandId/issuedAt，重试replayed不再发布。V2仍需确保跨重启/重放可用稳定事务键，不能把fedAt+foodId猜成唯一键。当前kind只有粗类别，不能冒充细粒度preset typeId。

以上支持复用已确认成功边界，但不证明r3要求的完整事件契约已经存在。应扩展/适配可信业务事实，不能在renderer拼装假eventId。无映射或视觉能力未ready时，用户已完成日常/喂食的业务事实照常有效，主题层报告unsupported/ineligible；不能因表现失败回滚真实完成或库存事务。

上述§9仅固定旧动画基线ff711d9，不代表用户当前main接口；当前main已完成独立只读核查，结论如下。不能据旧基线没有细ID断言当前产品没有预设。最终source-contract必须绑定真实当前源码commit与接口证据，未核定前保留待接入，不按标题或宽kind猜coffee/fitness。

## 10. 独立review身份与恢复澄清

sourceInstance在本契约是稳定业务来源命名空间，不是连接、进程或投递epoch；deliveryGeneration另存用于丢弃旧回调。全局已处理业务实例账本先于theme/mapping/source投影核对。同事务即使重连换epoch、换eventId或改变映射投影，也不能成为新来源重新续时。跨业务账户/命名空间的业务ID唯一性须由正式接入契约保证，不将两个不同账户的同号事务误合并。

恢复分两类：从未接纳过的历史记录首次导入/恢复同步，按建议不新激活当前主题；已接纳来源账本在进程重启后恢复，只恢复原截止尚未到期的事实资格，绝不重给完整时长。自动重新显示剩余主题是否允许可另作为产品恢复政策待批；无论显示与否，不删除真实业务事实、不延长截止。§5的“恢复同步不自动激活”针对前一类历史事件，不禁止恢复已存在账本的原剩余资格。

### 当前事件身份的最后边界

最终审计逐文件核查12份，其中10份schema/domain/事件接口与ff711d9一致，UI增加历史展示。自由occurrenceId在撤销后可能被复用，因此不能永久以原始occurrenceId压掉之后真正的新完成。r3的businessInstanceId必须代表语义上的完成实例/代际（例如由上游提供稳定completion identity与revision关系），而不是未经适配的V1原始occurrenceId。防重复续时建议只适用于同一个语义完成实例；真正的新完成代际与重复/编辑如何区分，必须由业务事务明确提供，主题层不能猜。未建立该身份契约前，不激活相关来源。

当前postcommit事实说明canonical事务已提交；本轮没有认证磁盘durable outbox。r3要求的持久幂等/恢复是新增完成条件，不能写成V1已保证。已有预设设计应先定位并关联稳定ID，不能仅因源码未找到目录就新造用户预设。

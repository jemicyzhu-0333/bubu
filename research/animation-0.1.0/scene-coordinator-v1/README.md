# SceneCoordinator v1: executable decision module

This is a new, independent, synchronous JavaScript module. It produces a plan; it does not render, detect OS activity, load assets, control face owner, mutate business records or consume inventory. Frozen runtime and prior policy directories are unchanged. No production mapping, artwork readiness or AI/coffee priority is asserted by test fixtures.

## API

- `createSceneCoordinator(config, {selectBackground})`: explicit recipe readiness, resource declarations, complete pair rules and bounded overlay capacity. `selectBackground(snapshot)` is injected product selection policy; it gets local date/time band/time zone and candidate IDs and runs exactly once per focus start. Caller is responsible for trusted calendar context. There is no built-in date-to-art policy or random default.
- `startFocus({sessionId, localDate, timeBand, timeZone, candidateIds}, trustedUtcNowMs)`: captures immutable selection snapshot and unique selection token. Selector failure or unavailable selection locks a blocked session; no fallback selection. End and explicitly start another session to retry. `endFocus(sessionId, selectionToken, now)` checks exact current identity, including the generated token if a caller reuses its session ID. Reentrant API calls from a selector are rejected; selectors must be synchronous. No implicit pause/restart persistence semantics.
- `setSourceGeneration(sourceId, generation, enabled, now)`: generation must strictly advance. Clears only that registered producer. Detection-off caller advances all detection producers in its authoritative scope; routine/feed/manual/needs remain independent. A producer must first be enabled before accepting snapshots.
- `applySnapshots([{sourceId,generation,revision,facts}], now)`: atomically replaces each included producer's complete current snapshot, not a patch. Facts are `{id,key,observedAt,expiresAt}` with optional opaque provenance. Omission within that producer revokes the fact. An empty snapshot revokes that producer only. Older generation/revision is ignored; identical revision with different facts is rejected. Feed/routine success and dedup remain the ledger's responsibility.
- `plan(now)`: recomputes current TTL eligibility and resource arbitration, retaining suppressed facts. All time inputs are nondecreasing trusted UTC milliseconds, independent of animation clock. Call before displaying or committing resumed work. Output is `kind: scene_plan`, with `visible:false` and `performing:false`; `selected` means selected for planning only. Contains locked `base`, `overlays`, `mainAction`, `face`, `resourceOwners`, current facts and diagnostics.
- `themeProjectionSnapshot(ledger.project(now), {sourceId,generation,revision})`: adapts each active ledger source, preserving exact source identity, completion generation, revision and deadline. Assign a monotonically increasing producer revision when publishing a changed full snapshot. It does not reapply duration policy and never consumes business events.

`planGeneration` changes only when the display plan changes, avoiding animation restarts for unchanged displays. `validityGeneration` also changes with source revisions/generations or active fact changes. A future async bridge must capture both plus session selection token, re-run `plan(currentTrustedTime)` before commit, reject stale results and release only its own resources. No async work or leases exist inside this module, so it has no pending queue or async completion path to leak. This is not a claim that a renderer rollback transaction has been implemented.

## Policy and resource boundary

Recipes are explicitly approved/ready sustained-plan recipes with `factKey`, `kind` (`overlay`, `action`, `face`), `resources` and `mode: sustained`. Actions must claim `body.action`, faces `face.semantic`; overlays may only claim `overlay.*` or no exclusive resource. No recipe may claim `environment.base`. An action can additionally claim face and hand resources, atomically in a single plan. Optional recipe IDs can model coding/music via injected real-source snapshots; this module does not provide those detectors.

Every shared-resource pair requires an explicit winner. Every overlay pair requires either an explicit winner or `compatible` (approved visual/occlusion compatibility). Shared resources cannot be marked compatible. Cycles are rejected. The explicit `overlayOrder` controls bounded-capacity admission and must agree with overlay conflict winners. `layer` controls final compositing order. Nonconflicting independent recipe ordering is diagnostic only. No AI > coffee default exists. Fixture priorities are test-only, not approved product policy.

One-shot drink/feed actions, loops, wait queues, sparse-action schedules, retry/replay consumption, real body/hand animation and artwork are intentionally not implemented: declaring a one-shot mode rejects admission. Coffee decoration does not create a drink action. Unmapped or unready facts remain facts with diagnostics and produce no fake activation. No ready focus background means focus-bound recipes remain unselected.
